Stock Intelligence Platform#

ข้อกำหนดการพัฒนาแบบ Spec-Driven Development#

สถานะเอกสาร: ข้อกำหนดฉบับตั้งต้น
เวอร์ชัน: 0.1.0-th
วันที่จัดทำ: 30 กันยายน 2026
ภาษาหลักของ Backend: Go
Frontend: Next.js + TypeScript
สถาปัตยกรรม: Microservices + Event-driven + Pragmatic Ports & Adapters
ตลาดหลัก: ประเทศไทย / หลักทรัพย์จดทะเบียนใน SET

0. วิธีใช้เอกสารนี้#

ไฟล์นี้เป็นแหล่งอ้างอิงหลักสำหรับผลิตภัณฑ์และสถาปัตยกรรมของระบบ

ก่อนพัฒนาฟีเจอร์ ผู้พัฒนาหรือ AI coding agent ต้อง:

  1. อ่านเอกสารนี้ให้ครบ
  2. ระบุ Bounded Context และ Service ที่เป็นเจ้าของฟีเจอร์
  3. แก้ Requirement, Acceptance Criteria, API/Event Schema หรือ ADR ก่อนแก้โค้ด หากพฤติกรรมของระบบเปลี่ยน
  4. รักษาหลัก Data Ownership และทิศทาง Dependency
  5. คำนวณตัวเลขทางการเงินด้วยโค้ดที่ให้ผลแน่นอน
  6. เก็บ Evidence Lineage ของข้อเท็จจริงและผลคำนวณทุกตัว
  7. รันการทดสอบที่กำหนด และปรับเอกสารนี้เมื่อการตัดสินใจเปลี่ยน

ข้อกำหนดนี้แยกข้อมูลออกเป็น:

  • FACT: ข้อเท็จจริงที่มีหลักฐานโดยตรงจากแหล่งข้อมูล
  • INFERENCE: ข้อสรุปที่อนุมานจากข้อเท็จจริง
  • HYPOTHESIS: คำอธิบายที่เป็นไปได้ แต่ยังต้องหาหลักฐานเพิ่ม
  • CALCULATION: ผลลัพธ์ที่คำนวณจาก Input ที่ระบุได้และสูตรที่มี Version

1. บริบทของโครงการ#

1.1 บริบทของเจ้าของผลิตภัณฑ์และผู้พัฒนา#

ผู้พัฒนาหลักมีพื้นฐานดังนี้:

  • มีประสบการณ์ Software Engineering ประมาณ 4 ปี
  • ใช้งาน JavaScript, TypeScript และ Go
  • คุ้นเคยกับ Redis, Kafka, API, Testing, Distributed Systems และ Microservices
  • จบ Mechanical Engineering
  • สนใจการวิเคราะห์หุ้น Financial Engineering, AI Infrastructure, Data Center และพลังงาน
  • ต้องการสร้าง Portfolio Project ที่ใช้สมัครงาน Go Backend, FinTech, AI Platform และ Data Platform ได้

ระบบจึงควรแสดงความสามารถต่อไปนี้:

  • การเขียน Go ที่สอดคล้องกับแนวทางของภาษา
  • การแบ่ง Domain Boundary อย่างชัดเจน
  • Event-driven processing
  • การคำนวณตัวเลขที่เชื่อถือและตรวจซ้ำได้
  • การย้อนกลับไปหาแหล่งข้อมูลต้นทาง
  • AI Integration ที่มีระบบตรวจสอบ
  • Observability และ Deployment ที่พร้อมต่อยอดสู่ Production

1.2 วิสัยทัศน์ผลิตภัณฑ์#

สร้าง Stock Intelligence Platform ที่ติดตามข้อมูลบริษัทจากแหล่งปฐมภูมิอย่างต่อเนื่อง แปลงเอกสารเป็นข้อเท็จจริงที่มีหลักฐาน คำนวณตัวชี้วัดทางการเงินใหม่ เชื่อมการเปลี่ยนแปลงเข้ากับ Investment Thesis และแจ้งเตือนเมื่อข้อมูลใหม่อาจเปลี่ยนสมมติฐานอย่างมีนัยสำคัญ

1.3 คำถามหลักที่ระบบต้องตอบได้#

  1. อะไรเปลี่ยนไป?
  2. แหล่งข้อมูลใดยืนยันการเปลี่ยนแปลงนั้น?
  3. ตัวเลขหรือสมมติฐานข้อใดได้รับผลกระทบ?
  4. เหตุใดการเปลี่ยนแปลงนี้จึงอาจสำคัญ?
  5. ระบบมั่นใจเพียงใด?
  6. ยังมีประเด็นใดที่ตรวจสอบไม่ได้?

1.4 Use Case เริ่มต้น#

  • ติดตาม SET filings, SEC filings, Company IR, Presentation และข้อมูลตลาดที่เลือกใช้
  • รองรับหุ้นตัวอย่าง เช่น STPI, CCET, BGRIM, SPCG, KCE, HANA และ GUNKUL โดยไม่ผูกระบบกับรายชื่อเหล่านี้
  • ตรวจจับการเปลี่ยนแปลงด้านลูกค้า กำลังการผลิต Utilization, CAPEX, รายได้ Margin, EPS, Cash Flow, ความเสี่ยง Catalyst และสมมติฐาน Valuation
  • เก็บ Investment Thesis ที่มี Driver, Assumption, Risk, Catalyst, Evidence และ Invalidation Trigger ชัดเจน
  • สร้าง Alert ที่แยก FACT, CALCULATION, INFERENCE และ HYPOTHESIS

2. หลักการของผลิตภัณฑ์#

P-001 — หลักฐานมาก่อนคำอธิบาย#

ข้อกล่าวอ้างที่มีนัยสำคัญต้องเชื่อมกลับไปยัง Primary Source เมื่อมีแหล่งดังกล่าว Metadata ของแหล่งข้อมูลต้องมี URL, เวลาที่ดึงข้อมูล, เวลาที่เผยแพร่ถ้ามี, Document Hash และตำแหน่งในเอกสาร เช่น หน้า ตาราง แถว หรือ Text Span

P-002 — คำนวณตัวเลขด้วยโค้ด#

ตัวเลขทางการเงินต้องคำนวณด้วยโค้ดที่มี Version ห้ามมอบหมายให้ LLM เป็นผู้คำนวณค่าที่ถือเป็นข้อมูลทางการ ระบบต้องเก็บ Input, หน่วย, งวด, สกุลเงิน, Formula Version และ Output

P-003 — ข้อเท็จจริงและการตีความเป็นคนละ Record#

Fact ที่ดึงมาจากเอกสารและ Analyst Interpretation ต้องไม่ถูกเก็บเป็น Entity เดียวกัน การแก้ Inference ต้องไม่แก้ Fact ที่รองรับอยู่

P-004 — แต่ละ Domain เป็นเจ้าของข้อมูลของตัวเอง#

Microservice แต่ละตัวเขียนได้เฉพาะ Database ของตัวเอง Service อื่นต้องอ่านผ่าน API หรือ Event ที่เจ้าของข้อมูลเผยแพร่

P-005 — แจ้งเตือนเฉพาะข้อมูลที่มีความหมาย#

ระบบควรแจ้งเมื่อเข้า Threshold, Thesis Trigger หรือ Materiality Rule ที่กำหนด การมีเอกสารใหม่เพียงอย่างเดียวไม่ควรทำให้ผู้ใช้ได้รับ Notification เสมอไป

P-006 — ตรวจสอบย้อนหลังได้#

ทุกการ Extract, Correct, Calculate, Thesis Impact, AI Analysis และ Notification ต้องมี Audit Trail

P-007 — เปลี่ยน Infrastructure ได้#

Business Rule ต้องไม่ผูกกับ PostgreSQL, Kafka, HTTP Framework, LLM Provider หรือ Notification Channel รายใดรายหนึ่งโดยตรง

5. การตัดสินใจด้านสถาปัตยกรรม#

5.1 สถาปัตยกรรมที่เลือก#

  • แบ่ง Microservices ตาม Bounded Context
  • ใช้ Event-driven Communication สำหรับการกระจาย State Change
  • ใช้ REST หรือ gRPC สำหรับ Query และ Command ที่ต้องรอคำตอบทันที
  • ใช้ Pragmatic Ports & Adapters ภายใน Go Service
  • ใช้ DDD เฉพาะ Domain ที่มีความซับซ้อนเพียงพอ
  • Service เป็นเจ้าของ Database ของตัวเอง
  • ใช้ Transactional Outbox เพื่อ Publish Event อย่างเชื่อถือได้
  • ใช้ OpenAPI สำหรับ HTTP Contract
  • ใช้ AsyncAPI และ JSON Schema สำหรับ Event Contract
  • Backend Service แต่ละตัว Build และ Deploy ได้อย่างอิสระ
  • เก็บหลาย Go Modules ใน Monorepo และใช้ go.work ที่ Root สำหรับ Local Development

5.2 เหตุผลที่เลือก#

โครงการมีงานหลายชนิดที่มี Load และรอบการเปลี่ยนแปลงต่างกัน:

  • Source Collection เป็นงาน I/O สูง
  • Parsing และ AI Extraction ใช้ Compute สูง
  • Market Data เป็น Time-series
  • Financial Metrics ต้องใช้ Domain Rule ที่ให้ผลแน่นอน
  • Research และ Thesis มีความสัมพันธ์และ Audit History ซับซ้อน
  • Notification ต้องจัดการ Retry และพฤติกรรมเฉพาะแต่ละ Channel

ขอบเขตเหล่านี้เหมาะกับการแยก Service โดยยังรักษาโครงสร้างภายในแต่ละ Service ให้เรียบง่าย

5.3 ข้อจำกัดทางสถาปัตยกรรม#

  • Service ห้าม Query ตารางของ Service อื่นโดยตรง
  • ห้ามแชร์ Domain Model ข้าม Service
  • Shared Contract Package มีได้เฉพาะ Generated Transport Type ไม่ใช่ Business Entity ร่วมกัน
  • Event ที่ Publish แล้วแก้ไขไม่ได้
  • Breaking Change ต้องออก Event หรือ API Version ใหม่
  • ห้ามทำ Distributed Transaction ให้ใช้ Local Transaction, Outbox, Idempotency และ Compensating Action

15.3 ข้อกำหนด Collection#

  • เคารพ Rate Limit และข้อกำหนดของ Source
  • Retry Transient Error ด้วย Capped Exponential Backoff และ Jitter
  • Permanent Validation Failure ไม่ Retry อัตโนมัติ
  • เก็บ Retrieval Status และ Error Category
  • Hash Document Byte ก่อน Parse
  • Content ที่ Hash เหมือนกันถือเป็น Duplicate แต่ต้องเก็บ Discovery Metadata
  • เก็บ Parser และ Extractor Version

16. Thesis Impact Engine#

16.1 ประเภท Trigger#

  • Threshold: gross_margin < 0.06
  • Percentage Change: Revenue Growth ลดลงเกินค่าที่กำหนด
  • State Change: Project Status เปลี่ยนจาก Planned เป็น Delayed
  • Evidence Appearance: พบชื่อลูกค้าหรือโครงการใน Primary Source
  • Evidence Disappearance: ข้อมูลที่คาดว่าจะเปิดเผยไม่ปรากฏภายในช่วงเวลาที่กำหนด
  • Contradiction: หลักฐานใหม่ขัดกับ Assumption ปัจจุบัน
  • Scheduled Review: Thesis ไม่ได้รับการ Review ภายในกำหนด

16.2 Materiality#

LOW      ข้อมูลประกอบ แสดงบน Dashboard
MEDIUM   Thesis Item อาจต้องได้รับการ Review
HIGH     Assumption หรือ Valuation อาจเปลี่ยนอย่างมีนัยสำคัญ
CRITICAL เข้า Invalidation Condition หรือเกิดความเสี่ยงรุนแรง

Materiality ต้องมาจาก Explicit Rule หรือ Human-reviewed Mapping AI เสนอ Materiality ได้ แต่ห้ามเขียนทับผล Rule โดยไม่แสดงให้ผู้ใช้ทราบ

  • ใช้ Authentication ที่รองรับ OIDC/OAuth 2.0

  • Encrypt Managed Storage ขณะจัดเก็บ

24. Initial Requirements และ Acceptance Criteria#

REQ-001 — เก็บ Official Source Document#

Owner: ingestion

Acceptance criteria:

  • ตรวจ Source ที่ Configure ไว้ตาม Schedule ได้
  • ดาวน์โหลดเอกสารใหม่พร้อม URL, Timestamp, MIME Type และ SHA-256
  • ไม่เก็บ Content Byte ที่เหมือนกันซ้ำ
  • เก็บ Discovery Metadata แม้ Content ซ้ำ
  • Publish source.document_collected.v1 ผ่าน Outbox
  • แยก Transient และ Permanent Failure ได้ใน Log และ Metric

REQ-002 — Extract Financial Fact ที่ย้อนกลับไปหาหลักฐานได้#

Owner: document-intelligence

Acceptance criteria:

  • Parser บันทึก Version
  • Candidate Fact มี Value, Unit, Period, Taxonomy Key และ Evidence Location
  • Reviewer เปิดดูหน้าเอกสารหรือ Location ที่รองรับ Fact ได้
  • Reject Output ที่ไม่ผ่าน Schema
  • Candidate ไม่กลายเป็น Authoritative Fact อัตโนมัติ เว้นแต่ผ่าน Validation Rule ที่บันทึกไว้

REQ-003 — Verify และ Version Financial Fact#

Owner: fundamentals

Acceptance criteria:

  • Verify หรือ Reject Candidate ได้
  • Verification เก็บ Actor, Time และ Reason
  • Restatement สร้าง Version ใหม่โดยไม่ลบ Version เดิม
  • Verified Change Publish fundamental.facts_updated.v1

REQ-004 — คำนวณ Metric ที่ทำซ้ำได้#

Owner: metric-valuation

Acceptance criteria:

  • Calculation เก็บ Formula Version และ Input ID ทั้งหมด
  • รันซ้ำด้วย Input เดิมได้ Output เดิม
  • มี Test สำหรับ Unit, Period, Missing Value และ Rounding
  • Material Result Change Publish valuation.metric_changed.v1

REQ-005 — ตรวจ Thesis Impact#

Owner: research-thesis

Acceptance criteria:

  • ผู้ใช้กำหนด Measurable Thesis Trigger ได้
  • Incoming Metric Change ถูก Match กับ Active Trigger ที่เกี่ยวข้อง
  • ผลระบุ Thesis Item และ Materiality ที่ได้รับผลกระทบ
  • Trigger Evaluation เป็น Idempotent
  • เมื่อ Match แล้ว Publish research.thesis_impacted.v1

REQ-006 — สร้างคำอธิบายที่มีหลักฐาน#

Owner: ai-analyst

Acceptance criteria:

  • FACT Claim ทุกข้อมี Stored Citation อย่างน้อยหนึ่งรายการ
  • Calculated Value อ้าง Metric Service Result
  • แยก Fact, Calculation, Inference และ Hypothesis
  • แสดง Counter Evidence และ Unknown เมื่อมี
  • Reject หรือ Retry Schema-invalid Response ตาม Bounded Policy

REQ-007 — ส่ง Material Alert หนึ่งครั้ง#

Owner: alert

Acceptance criteria:

  • Materiality Rule เป็นผู้ตัดสินว่าจะส่ง Notification หรือไม่
  • Duplicate Upstream Delivery ไม่ทำให้ผู้ใช้เห็น Alert ซ้ำ
  • Audit Delivery Attempt และ Final Status ได้
  • Alert เชื่อม Thesis Item, Metric และ Evidence ได้

31. Glossary#

คำ ความหมายในโครงการ
Bounded Context ขอบเขต Domain ที่มีภาษา Model และ Ownership ของตัวเอง
Port Interface ที่ Application Core ต้องการหรือเปิดให้เรียก
Adapter Implementation เฉพาะ Technology ที่เชื่อม Port กับระบบภายนอก
Driving Adapter HTTP, gRPC, Kafka Consumer, CLI หรือ Scheduler ที่เรียก Application
Driven Adapter Database, Broker Producer, External API, Storage หรือ LLM ที่ Application ใช้

Inbox Consumer-side Record สำหรับป้องกัน Process Event ซ้ำ
Evidence Lineage เส้นทางจาก Claim หรือตัวเลขกลับไปหา Source Content และ Processing History
Thesis มุมมองการลงทุนแบบมีโครงสร้าง ประกอบด้วย Driver, Assumption, Risk, Catalyst และ Invalidation Trigger
Materiality ระดับที่ข้อมูลอาจกระทบ Thesis, Risk Assessment หรือ Valuation
Restatement Version ใหม่ที่เป็นทางการของ Financial Value ที่เคยรายงาน
