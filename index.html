Stock Intelligence Platform#

Spec-Driven Development — Product, Domain and Software Architecture Specification#

Document status: Baseline specification
Version: 0.1.0
Created: 2026-09-30
Primary implementation language: Go
Frontend: Next.js + TypeScript
Architecture: Microservices + Event-driven + Pragmatic Ports & Adapters
Primary market: Thailand / SET-listed securities

0. How to Use This Document#

This file is the primary source of truth for the product and its architecture.

Before implementing a feature, an engineer or AI coding agent must:

  1. Read this document completely.
  2. Identify the affected bounded context and owning service.
  3. Update the relevant requirement, acceptance criteria, API/event schema, or ADR before changing code when behavior changes.
  4. Preserve service data ownership and dependency direction.
  5. Implement deterministic financial calculations in code.
  6. Preserve evidence lineage for every extracted or calculated fact.
  7. Run the required tests and update this document when a decision changes.

This specification deliberately separates:

  • FACT: directly supported by a source document.
  • INFERENCE: conclusion derived from facts.
  • HYPOTHESIS: plausible explanation that still requires evidence.
  • CALCULATION: deterministic result produced from identified inputs and a versioned formula.

1. Project Context#

1.1 Product owner and developer context#

The primary developer has:

  • approximately four years of software engineering experience;
  • working knowledge of JavaScript, TypeScript, and Go;
  • experience or familiarity with Redis, Kafka, APIs, testing, distributed systems, and microservices;
  • an undergraduate background in Mechanical Engineering;
  • strong interest in investment analysis, financial engineering, AI infrastructure, data centers, and energy;
  • a goal to build a serious portfolio project that can support applications for Go backend, FinTech, AI platform, and data platform roles.

The system should therefore demonstrate:

  • idiomatic Go;
  • explicit domain boundaries;
  • event-driven processing;
  • reliable numerical calculation;
  • source traceability;
  • AI integration with verification;
  • production-oriented observability and deployment practices.

1.2 Product vision#

Build a Stock Intelligence Platform that continuously collects primary-source company information, converts it into verifiable structured facts, recalculates financial metrics, connects changes to an investment thesis, and sends evidence-backed alerts when new information may materially change an assumption.

1.3 Core outcome#

The system must answer:

  1. What changed?
  2. Which source proves it?
  3. Which number or assumption is affected?
  4. Why might it matter?
  5. How confident is the system?
  6. What remains unverified?

1.4 Initial use cases#

  • Track SET filings, SEC filings, company IR publications, presentations, and selected market data.
  • Monitor companies such as STPI, CCET, BGRIM, SPCG, KCE, HANA, GUNKUL, and other user-selected securities without hard-coding the product to those names.
  • Detect changes involving customers, production capacity, utilization, capex, revenue, margins, EPS, cash flow, risks, catalysts, and valuation assumptions.
  • Maintain an investment thesis with explicit drivers, assumptions, risks, catalysts, evidence, and invalidation triggers.
  • Produce alerts that distinguish fact, calculation, inference, and hypothesis.

2. Product Principles#

P-001 — Evidence before narrative#

Every material claim must link to a primary source when one exists. Source metadata must include URL, retrieval time, publication time when available, document hash, and exact document location such as page, table, row, or text span.

P-002 — Deterministic numbers#

Financial calculations must be performed by versioned code, never delegated to an LLM. The system must retain input values, units, periods, currency, formula version, and output.

P-003 — Fact and interpretation are different records#

Extracted facts and analyst interpretations must not be stored as the same entity. Updating an inference must not modify its underlying facts.

P-004 — Domain ownership#

Each microservice owns its domain data and writes only to its own database. Other services consume its API or published events.

P-005 — Material alerts#

The system should alert when a defined threshold, thesis trigger, or material information rule is met. It should not notify merely because a document exists.

P-006 — Auditability#

Every extraction, correction, calculation, thesis impact, AI analysis, and notification must have an audit trail.

P-007 — Replaceable infrastructure#

Business rules must not depend directly on PostgreSQL, Kafka, an HTTP framework, a specific LLM provider, or a specific notification channel.

3. Scope#

3.1 MVP scope#

  • User authentication through an external OIDC-compatible provider.
  • Company and security master data.
  • Watchlists.
  • Scheduled collection from selected official sources.
  • Raw document storage and deduplication.
  • PDF/HTML/XLSX parsing.
  • Financial fact extraction with review status.
  • Deterministic metric calculations.
  • Thesis creation and editing.
  • Rule-based thesis impact detection.
  • Evidence-grounded AI explanations.
  • In-app and at least one external notification channel.
  • Dashboard showing documents, facts, metrics, thesis, alerts, and citations.

3.2 Post-MVP scope#

  • Intraday and higher-frequency market data.
  • Portfolio construction and risk analytics.
  • Backtesting.
  • Collaborative research workspaces.
  • Paid subscriptions and API usage plans.
  • Broader international market coverage.
  • Advanced model evaluation and human feedback loops.

3.3 Explicit non-goals for MVP#

  • Automated trade execution.
  • Brokerage custody or money movement.
  • Guaranteed buy/sell recommendations.
  • Unreviewed AI-generated financial statements.
  • Ultra-low-latency trading infrastructure.
  • Rebuilding a general-purpose Bloomberg or Refinitiv terminal.

5. Architecture Decisions#

5.1 Selected architecture#

  • Microservices divided by bounded context.
  • Event-driven communication for state-change propagation.
  • REST or gRPC for synchronous queries and commands.
  • Pragmatic Ports & Adapters inside each Go service.
  • DDD patterns only where domain complexity justifies them.
  • Database ownership per service.
  • Transactional Outbox for reliable event publication.
  • OpenAPI for HTTP contracts.
  • AsyncAPI and JSON Schema for event contracts.
  • Independent build and deployment per backend service.
  • Monorepo containing multiple Go modules and a root go.work for local development.

5.2 Why this architecture#

The project contains several business capabilities with different workloads and change rates:

  • source collection is I/O-heavy;
  • parsing and AI extraction are compute-heavy;
  • market data is time-series oriented;
  • financial metrics require deterministic domain rules;
  • research and thesis management require rich relationships and audit history;
  • notifications require retries and channel-specific behavior.

These boundaries justify independent services while keeping each service internally simple.

5.3 Architecture constraints#

  • No service may directly query another service's tables.
  • Cross-service shared domain models are prohibited.
  • Contract packages may contain generated transport types, not shared business entities.
  • Events are immutable.
  • Breaking schema changes require a new event or API version.
  • Distributed transactions are prohibited; use local transactions, Outbox, idempotency, and compensating actions.

6.1 Services intentionally not created#

  • No separate Redis service in the domain model.
  • No separate repository service.
  • No EPS, EBITDA, DCF, or individual-ratio service.
  • No generic utility service.
  • No service split solely by controller, use case, or database table.

7. Service Communication#

7.1 Synchronous communication#

Use REST initially for:

  • browser-facing commands and queries;
  • low-volume internal lookups requiring an immediate response;
  • operational and health endpoints.

Use gRPC later only when profiling demonstrates a clear internal requirement or strongly typed streaming improves a defined workflow.

7.2 Asynchronous communication#

Use Kafka-compatible messaging for domain and integration events.

7.5 Messaging requirements#

  • At-least-once delivery is assumed.
  • Every consumer must be idempotent.
  • event_id is the idempotency key.
  • Poison messages move to a dead-letter topic after bounded retries.
  • Events must carry correlation and causation IDs.
  • Message payloads must not contain secrets.
  • Producers publish through a Transactional Outbox.
  • Consumers record processed event IDs or use an equivalent inbox pattern.

8. Data Ownership and Storage#

8.1 Storage choices#

Workload Initial store Evolution trigger
Transactional domain data PostgreSQL Retain unless a measured limitation exists
Semantic document retrieval PostgreSQL + pgvector Dedicated vector store only after measured need
Raw files S3-compatible object storage Retain
Cache and distributed locks Redis Retain or managed equivalent
Event log Kafka-compatible broker Retain
Market/time-series analytics PostgreSQL initially Add ClickHouse when query volume and retention justify it

8.2 Database ownership#

Each service owns a distinct database or logical schema and credentials. A single PostgreSQL cluster may host multiple service databases in development and early production, but ownership boundaries remain enforced.

8.3 Financial precision#

  • Do not use binary floating point for money or financial ratios persisted as authoritative results.
  • Use a decimal library or integer minor units where appropriate.
  • Store currency and unit with every financial fact.
  • Store reported value separately from normalized value.
  • Preserve the original sign and presentation when parsing statements.

10. Financial Calculation Rules#

10.1 Initial metrics#

  • Revenue growth: YoY, QoQ, MoM when the source frequency permits.
  • Gross profit and gross margin.
  • EBITDA and EBITDA margin, only when EBITDA definition is documented.
  • EBIT and EBIT margin.
  • Net profit and net margin.
  • Basic and diluted EPS.
  • CFO.
  • CAPEX.
  • FCF = CFO - CAPEX using an explicitly defined CAPEX mapping.
  • Net debt.
  • ROE and ROIC with documented denominator convention.
  • P/E.
  • EV/EBITDA.
  • Price-to-book.
  • DCF scenarios.

10.2 Calculation requirements#

Every calculated metric must retain:

  • formula name and version;
  • exact input fact IDs;
  • period alignment;
  • unit conversions;
  • currency conversion rate and date when applicable;
  • treatment of negative or missing values;
  • rounding mode;
  • result precision;
  • calculation timestamp.

10.3 Restatements#

When a company restates prior data:

  1. Do not overwrite the historical record silently.
  2. Create a new restatement version.
  3. Mark the prior version as superseded.
  4. Recalculate dependent metrics.
  5. Emit fundamental.facts_updated.v1 with a restatement flag.
  6. Re-evaluate affected thesis assumptions.

11. AI Analyst Specification#

11.1 Allowed responsibilities#

  • Extract candidate facts from documents.
  • Classify text and document sections.
  • Link statements to citations.
  • Summarize verified facts and deterministic calculations.
  • Identify possible thesis impacts.
  • Generate hypotheses clearly labelled as hypotheses.
  • Identify conflicting evidence and unanswered questions.

11.2 Prohibited responsibilities#

  • Invent missing financial values.
  • Calculate authoritative metrics without the Metric service.
  • Present inference as fact.
  • Remove uncertainty or source conflict from the final result.
  • make autonomous trade-execution decisions.
  • cite a document that was not retrieved and stored.

11.3 Accuracy-first checks#

Every material analysis follows six checks:

  1. SOURCE: prefer primary sources and record the origin of every important claim.
  2. FACT VS INFERENCE: classify fact, calculation, inference, and hypothesis explicitly.
  3. NUMBER: validate unit, currency, period, comparison basis, and formula.
  4. BRIEF: follow the requested company, timeframe, metrics, and output constraints.
  5. COUNTER-CHECK: search for conflicting or disconfirming evidence.
  6. HUMAN: expose what remains unknown and leave the final investment decision to the user.

12. Internal Architecture of Each Go Service#

12.1 Selected pattern#

Use Pragmatic Ports & Adapters.

  • Core packages contain domain rules and application use cases.
  • Input adapters invoke the application.
  • Output adapters implement interfaces required by the application.
  • main.go is the composition root.
  • Interfaces live close to the consuming package.
  • Folder depth is added only when the domain requires it.

12.2 Dependency direction#

flowchart LR
    HTTP[HTTP / gRPC / Kafka Consumer] --> APP[Application Use Cases]
    APP --> DOMAIN[Domain Rules]
    APP --> PORT[Required Interfaces]
    PG[PostgreSQL Adapter] --> PORT
    KAFKA[Kafka Producer Adapter] --> PORT
    API[External API Adapter] --> PORT

The domain and application core must not import infrastructure packages.

12.3 Clean Code, Clean Architecture, and Ports & Adapters#

Concept Role in this project
Clean Code Naming, small coherent APIs, explicit errors, focused functions, readable tests, minimal duplication
Clean Architecture Dependency rule: infrastructure depends on the business core
Ports & Adapters Concrete organization for connecting HTTP, Kafka, databases, external APIs, storage, and LLMs to the core

The project does not require identical layers in every service:

  • Gateway and simple CRUD behavior can use handlers plus a small application package.
  • Fundamentals, valuation, and thesis services use richer domain models.
  • Ingestion and document processing use pipeline-oriented application code with ports for sources and sinks.

12.5 Go coding rules#

  • Use context.Context as the first parameter for I/O and request-scoped operations.
  • Wrap errors with meaningful operational context.
  • Do not create a generic utils or common package.
  • Prefer small interfaces owned by the consumer.
  • Accept interfaces and return concrete types where practical.
  • Keep transport DTOs outside domain entities.
  • Do not expose database structs as public API responses.
  • Validate at trust boundaries.
  • Make side effects explicit.
  • Use dependency injection through constructors; no global mutable service locator.
  • Keep main.go focused on configuration, wiring, lifecycle, and shutdown.

  • Each backend service has its own go.mod.
  • Root go.work is for local development only.
  • Service deployments must not depend on go.work.

  • Generated contract types and narrowly scoped technical libraries may be shared only after a proven need.

14.5 API conventions#

  • JSON request and response bodies.
  • UTC timestamps in APIs; user interface renders Asia/Bangkok by default.
  • Cursor pagination for unbounded lists.
  • RFC 7807-style problem details for errors.
  • Idempotency key required for retryable external commands.
  • Optimistic concurrency on editable thesis resources.
  • OpenAPI is updated before implementation when a public contract changes.

15. Source Collection Pipeline#

15.1 Processing stages#

discover
  → fetch
  → hash
  → deduplicate
  → store raw document
  → register metadata
  → parse
  → extract candidate facts
  → validate schema and units
  → persist candidates
  → human/rule verification
  → publish verified updates

15.2 Source adapter contract#

Every source adapter must implement equivalent capabilities:

type Source interface {
    Discover(ctx context.Context, cursor Cursor) ([]DocumentRef, Cursor, error)
    Fetch(ctx context.Context, ref DocumentRef) (Document, error)
}

15.3 Collection requirements#

  • Respect source rate limits and terms.
  • Retry transient errors with capped exponential backoff and jitter.
  • Do not retry permanent validation failures automatically.
  • Store retrieval status and error category.
  • Hash document bytes before parsing.
  • Treat identical hashes as duplicate content while preserving discovery metadata.
  • Retain parser and extractor versions.

16. Thesis Impact Engine#

16.1 Trigger types#

  • Threshold: gross_margin < 0.06.
  • Percentage change: revenue growth deteriorates by more than a configured amount.
  • State change: project status moves from planned to delayed.
  • Evidence appearance: a named customer or project appears in a primary source.
  • Evidence disappearance: expected disclosure is absent for a defined period.
  • Contradiction: new evidence conflicts with a current assumption.
  • Scheduled review: thesis has not been reviewed within a configured interval.

16.2 Materiality#

Initial materiality levels:

LOW      informational; dashboard only
MEDIUM   thesis item may require review
HIGH     assumption or valuation may materially change
CRITICAL invalidation condition or severe risk trigger

Materiality must be derived from explicit rules or a human-reviewed mapping. AI may propose materiality but cannot silently overwrite the rule-based result.

18. Security and Privacy#

  • Use OIDC/OAuth 2.0 compatible authentication.
  • Enforce authorization in the owning service, not only in the gateway.
  • Do not place access tokens, credentials, private document contents, or personal data in events.
  • Store secrets in a secret manager in production.
  • Encrypt traffic in transit.
  • Encrypt managed storage at rest.
  • Validate uploaded and downloaded file types and sizes.
  • Apply egress allowlists to collectors where practical.
  • Maintain audit logs for verification, thesis edits, and notification actions.
  • Define data retention and deletion policies before supporting team workspaces.

24. Initial Requirements and Acceptance Criteria#

REQ-001 — Collect an official source document#

Owner: ingestion

Acceptance criteria:

  • A configured source can be checked on a schedule.
  • A new document is downloaded and stored with URL, timestamps, MIME type, and SHA-256.
  • Identical document bytes are not stored twice.
  • Discovery metadata is retained even when content is duplicated.
  • A source.document_collected.v1 event is published through the Outbox.
  • Transient and permanent failures are distinguishable in logs and metrics.

REQ-002 — Extract a traceable financial fact#

Owner: document-intelligence

Acceptance criteria:

  • The parser records its version.
  • A candidate fact includes value, unit, period, taxonomy key, and evidence location.
  • The source page or equivalent location can be shown to a reviewer.
  • Invalid schema output is rejected.
  • Candidate output does not become an authoritative financial fact automatically unless a documented validation rule permits it.

REQ-003 — Verify and version a financial fact#

Owner: fundamentals

Acceptance criteria:

  • A candidate can be verified or rejected.
  • Verification records actor, time, and reason.
  • A restatement creates a new version without deleting the old one.
  • A verified change publishes fundamental.facts_updated.v1.

REQ-004 — Calculate a reproducible metric#

Owner: metric-valuation

Acceptance criteria:

  • A calculation records formula version and exact input IDs.
  • Re-running with identical inputs produces the same output.
  • Units, periods, missing values, and rounding behavior are tested.
  • A material result change publishes valuation.metric_changed.v1.

REQ-005 — Detect a thesis impact#

Owner: research-thesis

Acceptance criteria:

  • A user can define a measurable thesis trigger.
  • An incoming metric change is matched against relevant active triggers.
  • The result identifies the affected thesis item and materiality.
  • Trigger evaluation is idempotent.
  • A match publishes research.thesis_impacted.v1.

REQ-006 — Produce an evidence-backed explanation#

Owner: ai-analyst

Acceptance criteria:

  • Every FACT claim has at least one valid stored citation.
  • Calculated values reference a Metric service result.
  • Fact, calculation, inference, and hypothesis are classified separately.
  • Counter evidence and unknowns are included when present.
  • Schema-invalid responses are rejected or retried within a bounded policy.

REQ-007 — Deliver a material alert once#

Owner: alert

Acceptance criteria:

  • Materiality rules determine whether a notification is sent.
  • Duplicate upstream delivery does not create duplicate user-visible alerts.
  • Delivery attempts and final status are auditable.
  • An alert links to the affected thesis item, metric, and evidence.

28. Definition of Done#

A feature is complete when:

  • Requirement and acceptance criteria are current.
  • Owning service is unambiguous.
  • Public API and event contracts are updated.
  • Database migration is backward-compatible or has an approved rollout plan.
  • Business rules have meaningful tests.
  • Adapters have required integration tests.
  • Logs, metrics, traces, and audit behavior are present.
  • Idempotency and retry behavior are defined.
  • Security and data ownership were reviewed.
  • User-facing evidence links work.
  • Documentation and relevant ADRs are updated.
  • The change has been exercised through its intended vertical slice.
